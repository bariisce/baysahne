# Push Notifications

## Overview

```
App (expo-notifications) ── POST /api/v1/devices ──▶ push_devices
Admin action / planner ──▶ notification_jobs (UNIQUE dedupe_key)
Worker: recover stuck → cancel stale → plan reminders → dispatch due → check receipts
Dispatch ──▶ Expo Push Service ──▶ FCM v1 (Android) / APNs (iOS)
```

No account is required. A device is identified only by a random installation id generated by the app, its Expo push token, platform, app version and permission state.

## Device registration (mobile/src/lib/push.ts)

- On launch and on every return to the foreground, the app reads the OS permission **without prompting**.
- The OS prompt appears only after the user taps **Bildirimleri aç** (home card or About screen). This matters on iOS, where the system prompt can be shown only once.
- When permission is granted, the app gets an Expo push token (`getExpoPushTokenAsync({projectId})`) and `POST /devices`. Token rotation (`addPushTokenListener`) triggers re-registration.
- When permission is revoked in system settings, the next sync tells the server, which deactivates the installation. A user who never opted in never sends anything.
- On the server, one installation id means one row. A token that shows up under a new installation (reinstall) is moved, and the old row is deactivated. `DeviceNotRegistered` errors from tickets or receipts deactivate the device.
- Push is unavailable on simulators and on web; the UI says so.

## Categories (editable in the admin panel)

| Category | Trigger | Dedupe key | Frequency cap |
|---|---|---|---|
| `new_production` | First publication of a production, if the editor ticks “notify” | `new_production:{production}` | yes |
| `performance_reminder` | Planner: for each lead time before a published, scheduled performance | `performance_reminder:{perf}:{lead}:{start_epoch}` | yes |
| `performance_cancelled` | Cancelling an announced, future performance | `performance_cancelled:{perf}` | no (important) |
| `performance_rescheduled` | Rescheduling an announced, future performance | `performance_rescheduled:{perf}:{n}` | no (important) |

The policy lives in the `notification_policy` table and can be changed by admins:
- reminder lead times (default 24 h; several allowed)
- `max_per_device_per_day` (default 3; 0 = unlimited)
- `broadcast_cooldown_minutes` between new-production broadcasts (default 60)

Templates are rendered at send time, so later edits apply. Only allow-listed placeholders are accepted.

## Reliability and duplicate prevention

1. **Enqueue**: the unique `dedupe_key` with `ON CONFLICT DO NOTHING` means the same event can never be enqueued twice, even when requests race.
2. **Claim**: `SELECT … FOR UPDATE SKIP LOCKED` lets several workers run safely.
3. **Re-validate before sending**. A job is cancelled with a reason instead of sent if:
   - the category was disabled;
   - the production is no longer published;
   - the performance was cancelled, unpublished, rescheduled or has started;
   - the lead time was removed;
   - it was superseded by a newer reschedule.
4. **Per-device reservation**: a `(job, device)` delivery row is committed *before* the provider call, so a crash or restart never re-sends to a device that may already have received it (at-most-once). Interrupted reservations are marked `interrupted` by stuck-job recovery.
5. **Provider outages** (network, 5xx, 429): the batch's reservations are released and the job is retried with exponential backoff (2, 4, 8, 16 min) up to 5 attempts, then marked `failed`. Admins can **retry** a failed job; devices that already received it are skipped.
6. **Late reminders**: if a performance is created after its reminder time (more than 15 minutes late), that reminder is skipped, not sent late.

## Local development

- `PUSH_PROVIDER=log` (default): the worker logs `[PUSH:log] …` lines and records deliveries with synthetic tickets. Nothing leaves the machine.
- Run one tick: `python -m app.worker --once`. Run continuously: `python -m app.worker`.
- Simulate a device:

```bash
curl -X POST http://localhost:8100/api/v1/devices -H "Content-Type: application/json" -d '{"installation_id":"local-test-device-0001","platform":"android","permission":"granted","push_token":"ExponentPushToken[local-test-0001]"}'
```

- Tests use `FakeProvider` (in memory, scriptable failures). Automated tests never send real notifications.

## Production setup (requires your accounts)

1. **Expo project**: run `npx eas-cli@latest init` in `mobile/`, which creates the project id. Set `EAS_PROJECT_ID` for builds (EAS env var or `.env`); it ends up in `extra.eas.projectId`.
2. **Android (FCM v1)**:
   - Create a Firebase project and add an Android app with your final package name.
   - Download `google-services.json` and supply it to EAS builds as a **file environment variable** named `GOOGLE_SERVICES_JSON` (never commit it).
   - In Firebase → Project settings → Service accounts, generate a key and upload it with `eas credentials` → Android → *Google Service Account Key for FCM V1*. Do not store this key in the repository.
3. **iOS (APNs)**: `eas credentials` → iOS → Push Notifications. EAS can create and upload an APNs key from your Apple Developer account, or you can upload an existing `.p8`.
4. **Server**: set `PUSH_PROVIDER=expo`. If you enable *Enhanced Push Security* in the Expo dashboard, also set `EXPO_ACCESS_TOKEN` as a secret.
5. **Run the worker** as its own always-on process (container `worker` in docker-compose, or a systemd service) with the same environment as the API.
6. Before any real broadcast, test with an internal build on your own device.

## Troubleshooting

| Symptom | Check |
|---|---|
| App says notifications are “not supported” | Simulator or web; use a physical device and a development or production build (not Expo Go) |
| Registration `error` in the app | `EAS_PROJECT_ID` missing from the build; the API is unreachable from the device |
| Job stays `pending` | Is the worker running? Look at `next_attempt_at` (backoff or cooldown) in **Bildirimler → Gönderim geçmişi** |
| Job `cancelled` | `cancel_reason` explains why (e.g. `performance_rescheduled`) |
| Many `error` deliveries with `DeviceNotRegistered` | Normal after uninstalls; those devices are deactivated automatically |
| `InvalidCredentials` / `MismatchSenderId` | FCM/APNs credentials in EAS do not match the build's identifiers |
